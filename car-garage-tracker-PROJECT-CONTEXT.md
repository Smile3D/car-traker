# Car Garage Tracker — контекст проекта

Этот документ — синтезированное описание архитектуры и бизнес-правил проекта, собранное
по итогам ~72 итераций разработки. Предназначен как контекст/инструкция для Claude Code —
чтобы не reconstruct-ить решения заново из истории чата, а сразу знать "правила игры".

Полная история промптов (буквальные тексты, которые скармливались в Claude Code) —
в файле `car-garage-tracker-scaffold-prompt.md`. Этот документ — выжимка архитектуры,
а не список промптов.

---

## 1. Что это за продукт

Два независимых продукта в одном приложении:

1. **Особистий кабінет** (`account_type = individual`) — трекер обслуживания личного авто:
   учёт ТО/ремонтов, заправок, чеков, фотоотчётов, аналитика расходов.
2. **CRM для авто-площадок** (`account_type = business`) — мини-CRM для дилеров/лотов:
   инвентарь авто на продажу, воронка клиентов (продавцы/покупатели), сотрудники,
   аналитика прибыли, Telegram-публикация объявлений.

Оба продукта живут в одном Nuxt-приложении, с общей системой auth, разным UI/layout
в зависимости от `account_type`.

---

## 2. Технологический стек

- **Backend:** FastAPI + PostgreSQL + SQLAlchemy + Alembic + JWT-auth
- **Frontend:** Nuxt 4 + TypeScript + Pinia + Tailwind
- **Файлы:** Pillow для конвертации изображений в WebP (НЕ ffmpeg — сознательный выбор)
- **Графики:** Chart.js/vue-chartjs
- **Drag-and-drop:** vuedraggable (Kanban-доски)
- **i18n:** uk (по умолчанию) + ru, все тексты через ключи переводов
- **Docker:** backend + frontend + PostgreSQL, единый `docker-compose up`, volume для `/uploads`
- **Внешние интеграции:** Telegram Bot API (свой бот пользователя, не общий бот платформы),
  ПриватБанк публичный API курса валют (`api.privatbank.ua/p24api/pubinfo`)

## 3. Особистий кабінет — сущности

- **User** (`account_type=individual`) — обычная регистрация, email/password
- **Car** — марка/модель/год/пробег/VIN/fuel_type (простой enum: petrol/diesel/gas/gas_petrol —
  БЕЗ electric/гибридов, привязан к логике единиц измерения FuelRefill)
- **ServiceRecord** — записи ТО/ремонта (дата, пробег, тип, стоимость), табы "Історія ТО" /
  "Внеплановий ремонт" на странице авто
- **FuelRefill** — заправки: дата, литры, сумма, пробег (nullable), station_name (select
  популярных сетей АЗС Украины + "Інше" с ручным вводом — номинативное использование брендов,
  без логотипов)
- **Receipt** — чеки, загрузка фото с конвертацией в WebP (Pillow), опциональная привязка
  к ServiceRecord ИЛИ FuelRefill (взаимоисключающе, не оба сразу)
- Графики расходов (по месяцам / ТО vs Ремонт / по пробегу / накопительно) — вынесены
  в отдельный 3-й таб "Графіки" на странице авто
- Кнопка "Сформувати звіт" — модалка с редактируемым текстовым отчётом (без указания
  сумм/денег), копирование в буфер обмена

## 4. CRM для авто-площадок — сущности

### 4.1 Организационная структура (ключевой рефакторинг, промпт №46)

- **Company** — `id, name, business_phone, business_tax_id, owner_user_id`
- **User** расширен: `company_id` (FK Company, nullable), `role` (enum: `owner`/`employee`,
  осмыслен только если `company_id` заполнен)
- Все CRM-сущности (Listing, Client, ClientStage, SocialConnection, Position, DealHistory)
  принадлежат **company_id**, не `user_id` напрямую — так и владелец, и сотрудники видят
  общие данные компании

**Модель прав доступа (простая, единое правило):**
- `role=owner` — видит и может делать ВСЁ
- `role=employee` — видит весь основной функционал (Інвентар, Клієнти, Kanban, Налаштування
  компании) НАРІВНІ з владельцем, КРОМЕ:
  - управления сотрудниками (приглашение/увольнение) — только owner
  - управления списком должностей (Position) — только owner
  - управления органиграммой (reports_to) — только owner
- Дополнительно (промпт №72): employee может **редактировать/удалять/закрывать сделку**
  ТОЛЬКО по лотам, где он сам назначен ответственным (`seller.employee_id === self`) или
  лот "нічийний" (`employee_id = null`). Чужие лоты — только просмотр.
- **Аналітика и Дашборд** для employee показывают только ЕГО данные (не всей компании);
  для owner — вся компания. Это фильтрация именно на страницах статистики, НЕ ограничение
  доступа к самим данным (Інвентар/Клієнти видны всем полностью).
- **"Історія угод"** — тоже разграничена: owner видит всё, employee — только свои сделки.

### 4.2 Listing (лот на продажу)

Технические характеристики (марка, модель, год, пробег, VIN, тип кузова, коробка передач,
двигатель, тип палива — РАСШИРЕННЫЙ enum с гибридами/электро, ОТДЕЛЬНЫЙ от Car.fuel_type),
состояние (новое/б.у., комплектация — textarea), фото (галерея, WebP, до 15 шт, до 10MB
каждое, staging-загрузка прямо в форме создания лота ДО того как лот создан).

**Коммерческий блок:**
```
purchase_price (цена закупки)
+ additional_expenses (доп. расходы, редактируемое число)
= total_cost (вычисляемое)

sale_price (базовая цена, ДО скидки)
- discount_amount (скидка)
= "Ціна зі знижкою" (вычисляемое, ВСЕГДА видимый блок в разметке — 0 грн если скидки нет,
  чтобы не было layout shift)

net_profit = "Ціна зі знижкою" (или sale_price если скидки нет) − total_cost
```
Валидация: `discount_amount` не может превышать `sale_price` (иначе уход в минус).

**Статусы:** `draft → active → reserved → sold` (+ `removed` — тупиковая ветка, не часть
воронки). Переход в `sold` — ТОЛЬКО через `POST /listings/{id}/mark-sold` (отдельный
эндпоинт с финальной ценой), не обычный PATCH.

**Продавец создаётся АТОМАРНО вместе с лотом** — в форме "Додати лот" есть секция
"Дані продавця" (ім'я/телефон обов'язково, email/соцмережі опційно), один запрос
`POST /listings` создаёт и `Listing`, и связанного `Client` (seller) в одной транзакции.
Один лот = максимум один продавец (unique constraint), но может быть несколько покупателей.

### 4.3 Client (продавці/покупці)

`client_type`: seller/buyer. `listing_id` обязателен (клиент всегда привязан к лоту).
Поля: name, phone (обязательно, с маской +380 XX XXX XX XX), email (опц.), social_media
(опц.), notes, employee_id (nullable FK на User — ответственный).

**Точки входа создания:**
- Seller — ТОЛЬКО через форму "Додати лот" (не через доску напрямую)
- Buyer — через кнопку "+ Додати клієнта" на доске Клієнти, ИЛИ кнопку "Додати покупця"
  прямо со страницы лота (client_type/listing_id предзаполнены)

### 4.4 ClientStage — настраиваемые колонки Kanban

Отдельно для seller и buyer (два независимых набора). Владелец может переименовывать,
добавлять, удалять (заблокировано если есть клиенты в этой стадии — 409), менять порядок
через drag-and-drop колонок целиком. Дефолтные стадии при первом заходе:
- Seller: Перший контакт → Огляд авто → Узгодження умов → Авто прийнято → Угода завершена
- Buyer: Лід → Перегляд авто → Переговори → Резерв → Угода закрита (+ Відмова)

### 4.5 Position — настраиваемые должности сотрудников

Аналогично ClientStage — владелец создаёт свой список названий должностей (не enum),
назначает при создании/редактировании сотрудника.

### 4.6 Employee = User (role=employee), не отдельная таблица

После рефакторинга №46 старая отдельная таблица Employee слита с User. Дополнительные
поля на User: `first_name, last_name, phone, social_links` (JSON-массив, динамический
список полей в UI), `position_id`, `reports_to_id` (self-referencing FK, органиграмма).

`is_active=false` при увольнении (не физическое удаление — сохраняет историю назначений).
При увольнении с назначенными клиентами — ОБЯЗАТЕЛЬНАЯ модалка массового перепризначення
(на другого сотрудника или "без відповідального"), иначе клиенты "теряются" незаметно.

### 4.7 EmployeeInvite — приглашение по ссылке

`token (uuid4), email (опц.), position_id (опц.), expires_at (+7 дней), used_at, is_revoked,
cancellation_reason (опц.)`. Регистрация по `/register?invite={token}` — третий сценарий
регистрации (отдельно от `/register` и `/register?type=business`), НЕ создаёт новую Company,
присоединяет к существующей, `role=employee`. После регистрации по инвайту — редирект на
Налаштування (мягкий онбординг, не блокирующий) для заполнения "Мій профіль".

### 4.8 DealHistory — неубиваемый журнал сделок

**Ключевая архитектурная идея:** снапшот данных (скопированные значения: имя/телефон
продавца-покупателя, марка/модель, `employee_name` текстом), НЕ foreign key на живые записи
(кроме `employee_id`, который хранится ДОПОЛНИТЕЛЬНО к `employee_name` — nullable FK,
`ON DELETE SET NULL`, именно для будущей точной агрегации статистики по менеджеру).
`listing_id` тоже `ON DELETE SET NULL`. Создаётся АВТОМАТИЧЕСКИ при `mark-sold` или
переходе в `removed`. READ-ONLY, без единого DELETE-эндпоинта — переживает удаление
лота из Архива. Разграничение доступа как у Аналітики (owner всё, employee — своё).

### 4.9 Архів — отдельный от Інвентаря модуль

Інвентар по умолчанию показывает только `draft/active/reserved` (декluttered). Лоты
в `sold/removed` живут в `/crm/archive` — отдельная таблица с колонками включая
"Менеджер" (кто продал). На детальной странице архивного лота скрыты "Редагувати"/
"Видалити" (только массовое удаление из списка Архива, с чекбоксами и bulk-эндпоинтом).
При архивации лота — связанный клиент пропадает с Kanban-доски Клієнти (но НЕ из
таблицы "Список" и НЕ физически удаляется).

### 4.10 SocialConnection — Telegram-интеграция

Свой бот пользователя (через @BotFather, не общий бот платформы) — `bot_token`
ЗАШИФРОВАН (Fernet, отдельный ключ шифрования, не тот же что для JWT), никогда не
возвращается на фронт повторно. Подключение — в Налаштуваннях (с пошаговой инструкцией),
не на странице композера. Композер постов — текст + emoji-picker + фото (upload вручную
ИЛИ автоподстановка из данных лота через модалку с живым поиском, без денежных данных
в автосгенерированном тексте).

### 4.11 CompanyCurrencySettings — курс валют

Авто (ПриватБанк API, кэш с TTL ~6ч, готівковий курс coursid=5) ИЛИ ручной курс — выбирает
owner. Оба значения видны одновременно в Налаштуваннях, выбирается активный источник.
Отображается в хедере рядом с иконкой профиля. Только для отображения/ориентира — никакие
суммы в БД не конвертируются.

## 5. Сквозные архитектурные конвенции (важно соблюдать во всех новых фичах)

1. **Read-only по умолчанию, редактирование по кнопке** — паттерн применён к Listing и
   Client: страница/карточка открывается в режиме просмотра, кнопка "Редагувати" переводит
   в режим правки с локальным copy-before-edit state (чтобы "Скасувати" мог откатить).

2. **Kanban-доски:** полный список данных в сторе, НЕ отфильтрованный — Інвентар/Клієнти
   со статус-фильтром через query-параметр должны фильтровать НА ФРОНТЕ поверх полного
   списка, а не делать отдельный серверный запрос при каждом клике на фильтр (иначе
   Дашборд/Аналітика после визита на отфильтрованную страницу получают неполные данные).

3. **`getEmployeeDisplayName` utility** — единая функция для отображения имени сотрудника
   (`{first_name} {last_name}` с fallback на email) — использовать ВЕЗДЕ (select'ы, карточки,
   таблицы), не дублировать логику в разных компонентах.

4. **Атомарные транзакции** там, где создаются связанные сущности одним действием
   (Listing + seller Client) — либо обе части создаются, либо откатываются обе.

5. **Двойная валидация** (фронт + бэкенд) на всех бизнес-правилах, которые теоретически
   можно обойти прямым запросом к API (доступ по ролям, скидка не больше цены, и т.п.) —
   фронт для UX, бэкенд как источник истины.

6. **Настраиваемые сущности вместо enum**, когда бизнес-логика у разных пользователей
   отличается (ClientStage, Position) — с защитой от удаления занятой записи (409 Conflict).

7. **Снапшот vs живая ссылка** — для исторических/архивных записей (DealHistory) хранить
   скопированные значения, не FK, кроме случаев где нужна будущая агрегация (тогда
   дублировать: и FK nullable SET NULL, и текстовый снапшот).

8. **i18n везде** — ни одного нового текста без ключа перевода (uk/ru).

9. **Non-interactive команды** при генерации через Claude Code (`-y`/`--yes` флаги) —
   чтобы не зависать на интерактивных промптах установки.

## 6. Соглашения по коду для этого проекта (Vue 3 / Nuxt 4)

Стек проекта — Vue 3 + Nuxt 4 + Pinia + TypeScript. Соблюдать при любых новых фичах:

- **Composition API с `<script setup lang="ts">`** — исключительно, никогда Options API
- **Auto-imports Nuxt** — не импортировать вручную то, что Nuxt уже автоимпортирует
- **Composables с префиксом `use`** — `useAuthStore`, `useEmployeeInvites`, `useCurrencyRate`
- **Компоненты тонкие** — нетривиальная логика (загрузка данных, бизнес-правила,
  форматирование) выносится в composables, `<script setup>` в основном "склеивает" вещи
- **Pinia — setup-store синтаксис** (функциональный, как composable), не options-store —
  консистентно со стилем Composition API
  ```
  // Плохо: defineStore('cars', { state: () => ({...}), actions: {...} })
  // Хорошо: defineStore('cars', () => { const cars = ref<Car[]>([]); ... return {...} })
  ```
- **Реактивность:** `ref` для примитивов, `computed` для производных значений. `reactive`
  экономно, только для локальных сгруппированных объектов, которые никогда не
  деструктурируются. **Никогда не деструктурировать Pinia store или `reactive()` напрямую**
  без `storeToRefs` — теряется реактивность
- **Загрузка данных:**
  - `useFetch`/`useAsyncData` — для данных, нужных при первой загрузке страницы
    (SSR-релевантно), всегда со стабильным ключом
  - `$fetch` (через типизированный `useApi`-composable) — для императивных вызовов
    (store actions, обработчики кликов). **Никогда не использовать `useFetch` внутри
    store action**
  - Для приватных страниц за авторизацией, где SEO/SSR не важен — предпочитать
    клиентскую загрузку (`onMounted` или `useAsyncData` с `{ server: false }`), а не
    форсировать SSR
- **Props/emits:** всегда типизированные через `defineProps<{...}>()` и
  `defineEmits<{...}>()`. Никогда не мутировать prop напрямую — копировать в локальный
  state перед изменением
- **Именование компонентов:** multi-word PascalCase (`UserProfileCard`, не `Card`)
- **Watcher — последнее средство** — если задачу решает `computed`, использовать `computed`
- **Никаких сокращений** в именах (та же конвенция, что в глобальном CLAUDE.md):
  `isSubmitting`, не `isSub`; `handleDeleteClick`, не `onDel`
